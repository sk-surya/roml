## Requirements

Closed by Task 17a: `MinMaxConstraint` carries an explicit `relation` (`Exact` / `Epigraph` / `Hypograph`); exact equality compiles to a bounded selector formulation with binaries, while max-epigraph and min-hypograph compile to zero-binary rows; a test proves the exact and one-sided feasible sets differ in a model with no objective (D13).
- **SM-12.4** — absolute value, positive part, and clamp have explicit exact semantics. Closed by Task 17b: `AbsoluteValueConstraint` with an `AbsoluteValueVariant` (`Absolute` / `PositivePart` / `Clamp { lower, upper }`), each a bounded exact bridge with a documented reference formulation; validation rejects unbounded expressions and invalid clamp bounds.
- **SM-12.6** — exact product support is limited to binary-binary and binary times bounded linear scalar function. Closed by Task 17c: `BinaryProductConstraint` with `ProductOperand::{Binary, Linear}`; the builder accepts exactly Binary×Binary, Binary×Linear, and Linear×Binary, and validates the binary operand is a true binary variable.
- **SM-12.7** — continuous-times-continuous products are not mislabeled exact. Closed by Task 17c: a request with two continuous operands is a typed `ModelError`; no exact MILP path exists and no relaxation is emitted (test asserts the rejection and the absence of any compiled row).
- **SM-12.8** — construct APIs return stable handles/results and expose formulation diagnostics. Advanced by all three tasks: builders return a stable `Construct` handle plus a result variable handle; the compilation report records per-construct formulation decisions, M values, derivations, and bound sources.

These clauses are already closed by Plan 01 Task 15 — do not re-close or re-claim them.

## Waves and parallelization

This plan has three tasks and **one execution wave — strictly serial within the plan**:

- **Task 17a** (min/max tracer) first and alone: it proves the algebraic-construct vertical slice end to end (payload → builder → origin roles → bridge → session dispatch → tests → evidence), establishing the pattern Tasks 17b and 17c mirror.
- **Task 17b** (abs/positive part/clamp) strictly after Task 17a.

**Can the three tasks run in parallel? No — three independent reasons:**

1. **File sharing.** All three modify `src/construct/mod.rs`, `src/model/mod.rs`, `src/compiler/origin.rs`, `src/compiler/session.rs`, `src/lib.rs`, `src/advanced.rs`, and the two shared test files — parallel execution would produce overlapping edits on the same files.
2. **Pattern dependency.** Tasks 17b and 17c are written *against* the Task 17a pattern (payload shape, builder return shape, bridge structure, session dispatch arm, role naming). They read Task 17a's committed artifacts as their model.
3. **Evidence sequencing.** The evidence file appends per-task facts in order; the D13 difference proof (Task 17a) is the semantic foundation the abs/clamp and product exactness tests reference.

The packet's serial order (Tasks 15 → 16 → 17) plus the phase-level dependency (Plan 02 runs after Plan 01) means this plan exposes **no cross-task parallelism**. D26 (one active implementation phase) and the M3 WIP limit already bound the phase to a single branch.

## must_haves

Goal-backward verification (the ROADMAP P32 gate, verbatim):

> **Gate:** every construct has one semantic definition, complete origins, exact portable formulation, and explicit failure when bounds/support are insufficient.

**Truths (observable behaviors):**

1. **Every construct has one semantic definition.** `ConstructKind` carries exactly one exact payload per algebraic construct (`MinMaxConstraint`, `AbsoluteValueConstraint`, `BinaryProductConstraint`); the one-sided epigraph/hypograph relations are explicit fields of `MinMaxConstraint`, not a second representation of exact equality (SM-12.3, D13).
2. **Complete origins.** Every generated bridge variable/row for min/max, abs/positive-part/clamp, and products carries `EntityOrigin::Construct { construct, role }`; the Plan 01 `BridgeFinalizer` and `BackendSnapshot::validate` reject any unoriginated entity (D5, SM-02.5).
3. **Exact portable formulation.** Exact min/max use bounded selector formulations; abs/positive part/clamp and products use bounded exact bridges; no-binary max epigraph/min hypograph rows are distinct one-sided relations; never a silent relaxation (D13, SM-12.3/12.4/12.6).
4. **Explicit failure when bounds/support are insufficient.** No finite Big-M → `CompileError::UnboundedBigM { construct, expression }`; continuous×continuous exact product requests → typed `ModelError` with no compiled entities (SM-12.7); unqualified native under `NativeRequired` → `CompileError::UnsupportedFeature` (SM-13.4, D12, D23).
5. **Exactness is never inferred from objective context.** A test proves the exact and one-sided feasible sets differ in a model with no objective (D13).
6. **Algebraic constructs reject invalid inputs.** Continuous×continuous products, non-binary product operands, unbounded abs/minmax operands, and invalid clamp bounds are typed errors (SM-12.4, SM-12.7).
